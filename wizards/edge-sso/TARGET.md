## Cross-app constraints

> Derived from: param `descr` text (explicit "must match" wording, consistent
> across all three variants) + source repo `context/architecture/overview.md`
> (Token contract, Signing strategy sections).

Explicit (stated verbatim in every relevant param's `descr`):
- `SSO_AUDIENCE` — must be identical on auth-app and CDN filter for the chosen variant. Fail-closed: filter rejects **all** tokens if unset.
- `SESSION_COOKIE` — must be identical on both apps (default `sso_session`).
- `SSO_ISSUER` — if set, must be identical on both apps (validated only when both set it).
- **cookie variant only**: `SESSION_PUBLIC_JWK` on the CDN filter must be the exact public counterpart of `SESSION_SIGNING_KEY` on the auth-app (asymmetric keypair, not a shared secret).
- **gate-only and header variants**: `SESSION_SECRET` must be identical on auth-app and CDN filter (shared HMAC key, HS256).

Inferred (stated in source-repo prose, not literally in a param `descr`):
- `AUTH_PREFIX` on the CDN filter must align with whatever CDN rule routes that path prefix to the auth-app (overview.md, "Cross-domain — Option 3"). Not itself duplicated on the auth-app as a param, but the auth-app's routes live under this same prefix by convention (`/auth/**`).
- The CDN filter **must bypass** the auth prefix — otherwise the login flow redirect-loops (overview.md).

## Secrets

| Secret | Variant(s) | How obtained |
|--------|-----------|--------------|
| `SESSION_SECRET` | gate-only, header (both apps); cookie (auth-app only, signs flow cookies) | Wizard-defined random key → `secrets.pickOrCreate({ name, bytes: 32 })`. Bind the same secret id to both apps in gate-only/header. |
| `SESSION_SIGNING_KEY` + `SESSION_PUBLIC_JWK` | cookie only (auth-app private key + CDN filter public JWK) | Asymmetric keypair → `secrets.generateKeypair({ name, algorithm: "ES256" })`. Private half bound to auth-app as secret; public JWK value written as a plain env var on **both** apps. |
| `GOOGLE_CLIENT_SECRET`, `GITHUB_CLIENT_SECRET`, `MICROSOFT_CLIENT_SECRET`, `FACEBOOK_CLIENT_SECRET` | all variants, per enabled provider | User brings it (pasted external OAuth client secret) → `secrets.pickOrCreate()`. Optional — provider self-activates only if its secret is present. |
| `IDP_CERT` | all variants, if SAML enabled | User brings it (pasted IdP signing cert) → `secrets.pickOrCreate()`. |

No `data_type: "secret"` param is mandatory except `SESSION_SECRET` (gate-only/header) and `SESSION_SIGNING_KEY` (cookie) — both are the session-signing key and always required for whichever variant is chosen. All OAuth/SAML provider secrets are `mandatory: false` at the API level but are the de facto trigger for enabling that provider (see Profile/variant branches).

## Edge Storage

None. The source repo README/overview.md is explicit: **"KV is explicitly NOT used for config — too expensive per read."** No `data_type: "store"` params exist on any of the six templates. Unlike edge-totp, this wizard has no Edge Storage step.

## CDN wiring

Per `context/architecture/overview.md` §"Cross-domain — Option 3 (single domain via CDN-as-origin)":
- The **auth-app** is added as a CDN origin.
- A CDN rule routes the `AUTH_PREFIX` path prefix (default `/auth/**`) to the auth-app origin; everything else continues to the customer's existing origin.
- The **cdn-filter** is the CDN app / rule that gates all non-`AUTH_PREFIX` traffic, checking the session cookie.
- The filter's `AUTH_PREFIX` value and the CDN rule's routed prefix must be the same string — this is a wizard-authored CDN rule, not a template param, so the wizard must write it consistently when it creates the rule.
- IdP OAuth/SAML callback and ACS URLs are registered against this single CDN domain (`CANONICAL_HOST`) — stable across redeploys.

## Profile / variant branches

This is the central branch of the wizard — a genuine "whether to collect" decision, not a pick-vs-create the SDK already removes:

1. **Variant picker** (first step): gate-only / cookie / header. Determines which 2 of the 6 companion template IDs (from `context.get().companionTemplateIds`) the wizard uses for the rest of the flow. The other 4 are ignored entirely for this session.
   - gate-only → templates 738 (auth-app) + 739 (filter). Delivers nothing to origin; only pass/fail.
   - cookie → templates 740 (auth-app) + 741 (filter). Delivers a verifiable ES256 JWT cookie.
   - header → templates 742 (auth-app) + 743 (filter). Delivers `x-sso-*` headers; same HS256 signing as gate-only.
2. **Provider selection** (per variant, same for all three): user picks one or more of Google / GitHub / Microsoft / Facebook / SAML. Each selected provider makes its client-id/secret (and, for SAML, the IdP_* block) required in practice even though the API marks them `mandatory: false` — this is the fail-closed-in-practice case the intake instructions call out explicitly.
   - If Microsoft is selected and `MICROSOFT_TENANT` is left as the wildcard default (`common`/`organizations`/`consumers`), the wizard should nudge the user toward setting `MICROSOFT_ALLOWED_TENANTS` (security-relevant default called out in the param `descr` itself).
3. **cookie-only sub-step**: generate the ES256 keypair (`secrets.generateKeypair`) instead of the random-bytes secret used by the other two variants.
4. **Branding** (optional, all variants): `LOGIN_PAGE_*` tier-1 env vars. Purely cosmetic, safe to skip/default.
