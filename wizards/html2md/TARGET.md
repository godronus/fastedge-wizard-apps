## CDN wiring — corrected model

**This is resource-level configuration, not a path rule.** The first intake
pass assumed the wizard would use `cdn.rules.create` with a `fastedgeFilter`
(rule-scoped, and the bridge only allows `on_request_headers` /
`on_response_headers` there). Live data disproves that assumption.

Inspecting a real CDN resource (id `2296532`) that already has this exact
filter pattern wired up by hand shows the true shape — `options.fastedge`
lives directly on the **CDN resource**, not on a rule:

```json
// GET /cdn/resources/2296532 → options.fastedge
{
  "enabled": true,
  "on_request_headers":  { "enabled": true, "app_id": "817232", "interrupt_on_error": false, "execute_on_edge": true, "execute_on_shield": false },
  "on_response_headers": { "enabled": true, "app_id": "817232", "interrupt_on_error": false, "execute_on_edge": true, "execute_on_shield": false },
  "on_response_body":    { "enabled": true, "app_id": "817232", "interrupt_on_error": false, "execute_on_edge": true, "execute_on_shield": false }
}
```

`on_response_body` **is a real, live backend field** — it's just set via
`PUT`/`PATCH /cdn/resources/{resource_id}` (body: `{ options: { fastedge: {...} } }`),
not via `POST /cdn/resources/{resource_id}/rules`. (A separate rule on the same
account, id `23240025`, shows the rule-scoped `options.fastedge` only ever
carries `on_request_headers` in practice — consistent with the bridge's
rule-level restriction to headers-only hooks; resource-level is the wider
surface.)

**Platform gap — CLOSED.** The wizard bridge now has a resource-level intent for
this. `deployment.plan` accepts `cdnResourceFastedgeHandlers` — per-hook app
bindings across all 4 hooks (`on_request_headers`, `on_request_body`,
`on_response_headers`, `on_response_body`), each hook optionally bound to a
different app. `deployment.apply` GETs the resource, fails closed with
`conflict` if a requested hook already points at an app outside the wizard's
managed set, merges in the new bindings while preserving any hook the plan
doesn't touch, and PATCHes `options.fastedge`. Rollback reverts the PATCH to
its exact pre-apply value (including `null` if it was never set).

Implemented in `fastedge-frontend`:
`libs/features/src/lib/wizard-host/intents/{shared,deployment.handlers,intent-handler}.ts`,
documented in `docs/wizards/intent-catalog.md` (`deployment.plan` §
`cdnResourceFastedgeHandlers`). SDK types added in `fastedge-wizard-sdk/src/types.ts`
(`DeploymentPlanFastedgeHandlers`) — **not yet published**; this wizard depends
on a `@gcoredev/fastedge-wizard-sdk` release that includes it. Until that
release ships and the host change deploys to the portal, this wizard's
CDN-wiring step will not work end-to-end against the real portal (local mock-host
dev works today, since the mock host was updated in the same session).

For this wizard, the plan needs only one hook binding set (all three of
`on_request_headers` / `on_response_headers` / `on_response_body`, per
`instructions.md`), all pointing at the same single proxy-wasm app —
`on_request_body` is not needed here.
