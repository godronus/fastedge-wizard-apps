## Cross-app constraints

> Derived from: filter template `long_descr` (735, live API), the source repo
> README + `context/integration.md` + `context/architecture/storage-and-secrets.md`,
> and both `.env.example` files. All **stated explicitly**, not inferred.

Params appearing on **both** templates must carry the same value/secret id
(intersection of the two param lists):

- `MFA_SESSION_KEY` — secret. Create **once**, bind the same secret id to both apps. A mismatch fail-closes the filter (rejects every session).
- `MFA_AUDIENCE` — must be identical. **Asymmetry:** `mandatory:false` on the app, `mandatory:true` on the filter (fail-closed). When both are deployed, the wizard **treats it as required** and binds the same value to both. Should be the protected app's public URL, e.g. `https://app.example.com`.
- `MFA_SESSION_COOKIE` — must match (default `mfa_session`).
- `AUTH_PREFIX` — must match **and** must equal the CDN path rule routing to the app (default `/auth/totp`).
- `MFA_ISSUER` — optional; if set on one, must be set identically on both.

`MFA_LOGIN_URL` is **filter-only** (not shared).

## Secrets

Create each once via the portal; for shared secrets bind the same id to both apps.

- `MFA_SESSION_KEY` (both apps — **shared**, bind same id). HS256, 32+ bytes → `secrets.generate({ length: 32 })`.
- `HANDOFF_KEY` (app only). HS256, shared with the customer origin out-of-band.
- `ENROLL_API_KEY` (app only). Bearer token gating enroll.
- `GCORE_API_TOKEN` (app only). Real Gcore API token — user must paste (`secrets.create`/`pick`), not generate.
- `MFA_PROOF_SIGNING_KEY` (app only, **Profile B**). ES256 P-256 private key → `secrets.generateKeypair`; the public JWK feeds `MFA_PROOF_PUBLIC_JWK`.

## KV stores

App-only. Both `mandatory:true`, typed `string` (not `store`) — treat like store params:

- `KV_STORE_NAME`, `KV_STORE_ID` — pick/create a **single-tenant** store, then inject
  both `{ id, name }` into the app env **before** `deployment.plan()`.
  Do **not** use `newFastedgeStores` (no store-ref substitution at plan time).

## CDN wiring

Both apps must sit on the **same CDN resource** (same delivery domain) so
`mfa_session` is first-party host-only.

1. **App (734, origin):** create a CDN origin pointing at the app; add a path rule for `{AUTH_PREFIX}/*` (e.g. `/auth/totp/*`) routing to it.
2. **Filter (735, proxy-wasm):** attach as a CDN proxy-wasm application on the **"On request headers"** hook, covering the protected paths. It auto-bypasses `AUTH_PREFIX` + `/health`.

## Profile / variant branches

- **Profile A (default):** filter enforces `mfa_session`; zero origin code. No Profile-B params.
- **Profile B (opt-in):** app additionally signs a one-time ES256 proof; origin verifies via JWKS. Requires `MFA_PROOF_SIGNING_KEY` + `MFA_PROOF_PUBLIC_JWK` (both on the **app**), plus optional `PROOF_TTL` / `MFA_PROOF_COOKIE`.

The wizard should offer a Profile A/B selector and only collect the Profile-B params in branch B.

## Notes

- **Doc inconsistency (upstream):** the filter's `long_descr` (735) says Profile B sets
  `MFA_PROOF_SIGNING_KEY` on the *filter* and `MFA_PROOF_PUBLIC_JWK` on the *app*. The
  actual param lists put **both** on the app (734); the filter has neither. The source
  repo (`.env.example`, `storage-and-secrets.md`) agrees: both live on `otp-app`. Trust
  the param list. Wizard binds both Profile-B params to the app only.
- `MFA_AUDIENCE` mandatory-false-on-app / true-on-filter is the one asymmetry the plain
  `mandatory` flag can't express — handled in wizard logic, not metadata.
- Neither template carries `shared_across_apps` / `conditional-required` metadata
  annotations; shared params are detected by intersecting the two param lists (per
  `context/PARAM_CONSTRAINTS.md`).
- `KV_STORE_ID`/`KV_STORE_NAME` are `data_type:"string"`, not `"store"` — the wizard
  must special-case them as store bindings.
