---
name: wizard-intake
description: Fetch target template params from the Gcore API, reconcile with any source-repo docs, and write wizards/<name>/TARGET.md as a durable brief for the build phase. Run as step zero before copying a wizard template.
---

Understand a target FastEdge template before building a wizard for it.

## When to use

Run before copying `wizards/_template` or `wizards/_template-react`. Produces
`wizards/<name>/TARGET.md` — the param table and constraint brief that every
subsequent build step and agent reasons against, instead of re-discovering.

## Args

`[wizard-name] [template-id-or-name ...]` — all optional; confirm interactively if not supplied.

## Steps

### 0 — Confirm before doing anything

Ask the user in a single message:

1. **Wizard name** — the directory that will be created under `wizards/`. Must be
   kebab-case, no spaces. Example: `edge-totp`.

2. **Target templates** — one or more template IDs or names. **List the primary
   (launch) template first**, companions after. For CDN filter wizards (e.g.
   `edge-totp`) the filter app is the launch template even if it's `proxy-wasm`;
   the wasi-http companion comes second. Example: `735 734` or `"otp-filter" "otp-app"`.

3. **Source repo path** (optional) — absolute or repo-relative path to a clone of
   the template's source repository, if the user has one. The skill reads the
   README and any `context/` docs for human-facing constraint prose that the API
   doesn't expose. If not provided, the skill falls back to the template's
   `long_descr` and `descr` field on each param.

Do not proceed until wizard name and at least one template is confirmed.

### 1 — Fetch template details from the API

Use the `fastedge-assistant` MCP tool (`gcore_api`) for all API calls — it handles auth automatically. For each confirmed template, fetch full details:

```
GET /fastedge/v1/template/{id}
```

If the user supplied a name rather than an ID, first search via:

```
GET /fastedge/v1/template?limit=200
```

and match by exact name (case-insensitive). If multiple match, present them and
ask which to use.

Response fields to keep: `id` (from list call if absent in detail), `name`,
`short_descr`, `long_descr`, `api_type`, `binary_id`, `params[]`.

Each param: `{ name, data_type, descr, mandatory, metadata? }`. Parse `metadata`
as JSON where present (ignore parse errors, treat as `{}`).

**This is the same fetch used by `/sync-wizard-fixtures` Step 3 — do not
reimplement; factor or inline as needed.**

### 2 — Read source repo (if provided)

If the user supplied a source repo path, read:
- Top-level `README.md` or `README` — high-level description and setup steps
- Any files under `context/` — architectural constraints, shared-param rules,
  profile/variant documentation, fail-closed behaviour notes

Summarise only the constraint-relevant content: which params must match across
apps, profile/mode branches, secrets that must be shared, CDN wiring requirements.
Do not transcribe build or deployment instructions.

If no source repo is provided, derive constraints from the `long_descr` on the
template detail response and the `descr` on each param. Note what was inferred
vs stated.

### 3 — Reconcile and write TARGET.md

Write `wizards/<name>/TARGET.md`. Structure:

```markdown
# Wizard intake: <name>

> Generated by `/wizard-intake`. The param source of truth is
> `fastedge.templates.read` (see param table below). Runtime template
> identification uses `launchTemplateId` / `companionTemplateIds` from
> `context.get()` — the IDs below are for *your* understanding only;
> the shipped wizard must not hard-code them.

## Target templates

| ID | Name | api_type |
|----|------|----------|
| <id> | <name> | wasi-http / proxy-wasm |
| ... | ... | ... |

## Params — <template name> (id: <id>)

| Param | data_type | mandatory | default | descr |
|-------|-----------|-----------|---------|-------|
| NAME  | string    | true      |         | ... |
| ...   | ...       | ...       | ...     | ... |

(Repeat section for each template.)

## Cross-app constraints

> Derived from: [source repo README | template long_descr | param descr]

List params that must carry the same value on every app in the wizard group.
For each: state whether the constraint is explicit (annotated in metadata or
stated literally in docs) or inferred (described in prose as "must match" etc.).

Example:
- `MFA_SESSION_KEY` — must be identical on both apps (stated in README §3)
- `AUTH_PREFIX` — inferred: "both apps must share the auth routing prefix"

## Secrets

List params with `data_type: "secret"` or params the docs describe as secrets
even if typed `string`. Note: create each once and bind the same id to all apps.

For each secret, record **how the wizard obtains it** (one SDK call per secret — the host's
`pickOrCreate` owns the pick-vs-create choice, so never plan a `[Create]/[Pick]` pair):

- **User brings it** (reuse existing, or paste a real external token like a Gcore API token) →
  `secrets.pickOrCreate()`.
- **Wizard-defined random key** (HMAC/signing key at a chosen `bytes` strength) →
  `secrets.pickOrCreate({ name, bytes })` (`bytes` arms the create-inline Generate button).
- **Asymmetric keypair** whose public half the wizard needs (ES256) →
  `secrets.generateKeypair({ name, algorithm })`.

## KV stores

List params with `data_type: "store"` or params referencing a KV store name/id.
Each maps to `stores.pickOrCreate()` (user selects an existing store or creates one inline).

## CDN wiring

If the template README or descr describes CDN origin/rule setup, summarise it
here: which app is the origin, which proxy-wasm app is the filter, which hook,
and whether a specific CDN resource is expected.

## Profile / variant branches

If the template has a profile selector or mode switch, describe the branches and
which params become required or optional in each. This is *whether-to-collect* branching
(legitimate — the wizard decides if a resource is needed at all from earlier answers), distinct
from the *how-to-select* branch that `pickOrCreate` already removes. Flag any `mandatory: false`
secret/store that a specific profile actually requires (fail-closed behaviour).

## Notes

Anything not captured above: API shape surprises, mandatory-false params that are
actually required in practice, fail-closed behaviours, etc.
```

**Key invariant to state in every TARGET.md:** the IDs in the "Target templates"
table are for the agent's build-time understanding. The shipped wizard identifies
templates at runtime via `context.get().launchTemplateId` and
`context.get().companionTemplateIds` — never by hard-coded IDs.

### 4 — Write initial fixture templates

Write `wizards/<name>/fixtures/fastedge/templates.json` using the fetched template
data, but with **normalised IDs** so the mock host can derive launch/companion
context automatically:

| Position in the confirmed template list | Fixture id |
|-----------------------------------------|-----------|
| First (launch template)                 | 1         |
| Second (first companion)                | 2         |
| Third (second companion)                | 3         |
| N-th companion                          | N (max 19) |

The mock host's `context.get()` derives `companionTemplateIds` from all fixture
templates with id 2–19. Templates with id ≥ 20 are treated as regular platform
templates (available via `templates.list()` but not wizard companions).

The real template IDs (from the API) are documented in `TARGET.md` for reference
only. Never hardcode them in the wizard.

Each entry in the JSON array:
```json
{
  "id": <normalised>,
  "name": <template name>,
  "short_descr": <short_descr or "">,
  "long_descr": <long_descr or "">,
  "api_type": <api_type>,
  "binary_id": <binary_id>,
  "params": [ { "name", "data_type", "descr", "mandatory" }, … ]
}
```

Skip this step (and note it in the report) if template API calls failed.

### 5 — Report

After writing, output a brief summary:
- Where `TARGET.md` was written
- How many params were found per template
- How many cross-app constraints were identified (explicit vs inferred)
- Whether a source repo was used or only API data

If no portal access is available (API call fails), fall back to reading the
source repo only and note the limitations clearly in `TARGET.md`.

## Graceful degradation

| Available | Behaviour |
|-----------|-----------|
| Portal API + source repo | Full: API params + prose constraints |
| Portal API only | Baseline: API params + `long_descr`/`descr` for constraints |
| Source repo only | Partial: README/context docs only; no validated param list |

Never fail entirely. Always produce a `TARGET.md`, even if it's incomplete.
Mark clearly what's missing and why.
